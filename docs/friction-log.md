# Friction log

Entries go in this file only when a task actually breaks. A guessed complaint is not an entry. The Devpost bonus is for specific breakage a reviewer can check.

Day 1 is the repo, the license, the script, and this file. Nothing in that work called the MCP SDK, Strands, Bedrock, or Open-Meteo, so there are no entries yet. The first one is written the day the server, a tool, the page, or the agent fails, in the words of what we tried.

Wednesday 21 October we need five real entries, copied onto the submission form. If fewer than five things have broken by then, we do not invent the rest. We keep going until five real ones exist, or we submit the ones we have.

## Fields

Every entry uses these fields, in this order. They match the optional friction-log fields on the Devpost form.

| Field | What to write |
| --- | --- |
| Task | The job we were trying to finish |
| Steps | What we did, in order, including versions and the command |
| Expected | What the docs, the spec, or the script said would happen |
| Actual | What happened instead, including the error text |
| Severity | `blocker`, `major`, or `minor` |
| Workaround | What we did so the demo could continue |
| Change we want | One change for Amazon or the SDK. Name who should make it |

Severity:

- **blocker** — the demo or the judge path cannot be finished until this changes, or the workaround is something a judge would trip on
- **major** — we finished, but we had to leave the documented path
- **minor** — we finished on the documented path, and lost time to a wrong doc, a bad default, or a confusing error

Feature requests are a separate form, written on Wednesday, with urgency `Critical`, `Important`, or `Nice-to-have`. An entry here can become one of those requests. The request is not a substitute for the entry.
